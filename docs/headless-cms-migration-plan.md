# ヘッドレス CMS 移行計画書(案C / 推奨案)

作成日: 2026-07-24
対象サイト: KADOMA ART FES 公式サイト (https://kadoma-artfes.jp/)
現行構成: 静的 HTML + jQuery + data.json / GitHub → Cloudflare Pages 自動デプロイ

> 本書は `docs/wordpress-migration-plan.md`(案A)の比較検討を経て採用した**案C(ヘッドレス CMS)**の詳細計画書である。案A(WordPress)は有料サーバー再契約が必要になるため見送り、現行の Cloudflare Pages(無料)を維持したまま管理画面を追加する構成を採る。

---

## 1. 採用構成の全体像

```
┌─────────────────┐     コンテンツ入力(日本語フォーム)
│   microCMS       │ ←──────────────── 運営メンバー(Web知識不要)
│  管理画面 + DB    │
└────────┬────────┘
         │ ① 保存で Webhook 発火
         ▼
┌─────────────────┐     ② ビルド時に API から記事取得
│  Cloudflare      │ ←── Astro が静的HTMLを生成
│  Pages (無料)    │
│  ・本番: main     │ ──→ https://kadoma-artfes.jp/(既存URL維持)
│  ・開発: develop  │ ──→ プレビュー専用URL(本番に影響なし)
└─────────────────┘
         ▲
         │ ③ Instagram はフィード取得サービス経由で表示
┌─────────────────┐
│  Instagram       │
└─────────────────┘
```

### 確定した方針

| 項目 | 決定内容 |
|---|---|
| ホスティング | **Cloudflare Pages を継続(無料)** |
| サイト生成 | **Astro(静的サイトジェネレータ)を導入** |
| CMS | **microCMS**(日本製・日本語UI。代替候補: Newt) |
| 費用 | **月額 0 円**(microCMS 無料枠 3 席以内で運用) |
| 編集者 | **3 アカウント共有**(常時 2 名 + 1 枠を残り 3 名で交代利用) |
| URL | **現行 URL を完全維持**(`kadoma-artfes.jp/kaf_mmg.html` 等) |
| ブランチ | **本番(main)と開発(develop)を分離**、develop はプレビューURL |

---

## 2. なぜこの構成か

### なぜ Astro か
- 現行は素の HTML を Cloudflare が配信しているだけ。CMS の内容をページに反映するには「CMS から記事を取得して HTML を組み立てる」工程が必要になり、それを担うのが Astro。
- **ビルド(HTML 生成)は Cloudflare Pages が自動実行**するため、運営メンバーは一切触らない。
- CLAUDE.md にも「将来的な静的サイトジェネレータ(Astro 等)への移行の下地を作る」と明記されており、当初からの到達点と一致する。
- 現行の CSS(style.css 等)と jQuery プラグイン(Slick / Lightbox / Vivus 等)はそのまま流用できるため、**見た目は完全維持**できる。

### なぜ microCMS か
- 管理画面・ドキュメント・サポートがすべて日本語。非エンジニア向けの「フォーム入力」型で、WordPress のブロックエディタより迷いにくく、**レイアウトを壊す事故が起きない**。
- 現行 `data.json` の構造(edition / event / contest / news 等)をほぼそのまま API スキーマに移せる。フェーズ1〜3の資産が最大限活きる。
- (代替: Newt も日本製で同等。将来 microCMS の制限が問題になれば移行可。本計画は microCMS 前提で記述)

### なぜ案A(WordPress)ではないか
- WordPress は PHP + MySQL サーバーが必須 → ヘテムル等の**再契約(月1,100円〜)が発生**。
- 現行の無料・高速・自動デプロイという優れた基盤を捨てることになる。
- 非エンジニアの更新性は microCMS でも同等以上に達成できる(下記要望対応表参照)。

## 3. データ設計(microCMS API スキーマ)

> microCMS 無料枠は **API 数 5 個まで**。以下の **4 API**で全要望を満たし、1 枠を将来用に残す。
> 画像は転送量(無料 20GB/月)節約のため、原則 Cloudflare 側(リポジトリ or R2)に置き、microCMS には軽量画像と URL のみ格納する。

### API①: `site-settings`(オブジェクト形式 / 年度情報)
現行 data.json のトップ階層をそのまま移植。**年度更新時はここだけ触れば全ページに反映**。

| フィールド | 対応する現 data.json | 例 |
|---|---|---|
| edition_* | edition | 大会名 / 番号 / 年度ラベル |
| event_* | event | 開催日 / 時間 / 会場 / 入場料 |
| contest_* | contest | 募集ステータス / 締切 / 展示期間 / 応募フォームURL |
| marche_* | marche | マルシェ名 / 日程 / 会場 |
| organization_* | organization | 主催 / 共催 / 後援 |
| social_* | social | YouTube / Instagram URL |

### API②: `news`(リスト形式 / お知らせ)
現行 data.json の news 配列 + media.html を統合。

| フィールド | 内容 |
|---|---|
| date | 日付 |
| category | カテゴリ(イベント / コンテスト / メディア掲載情報) |
| text | 本文 |
| link | リンク先(任意) |

### API③: `editions-archive`(リスト形式 / 過去展示アーカイブ)【新機能】
「過去の展示を年度別ページで詳しく見せる」要望に対応。1 件登録すると 1 枚のアーカイブページ(例 `/archive/2024.html`)を自動生成。

| フィールド | 内容 |
|---|---|
| year | 開催年(URL・並び順に使用) |
| title | 大会名(例: KADOMA ART FES 4) |
| date_range | 開催期間 |
| description | 展示の紹介文 |
| hero_image | 代表画像 |
| gallery | ギャラリー画像(複数・繰り返しフィールド) |
| award_winners | 受賞作品情報(任意・複数) |

### API④: `sponsors`(リスト形式 / 協賛一覧)
現行 kaf_support.html にハードコードされている 30+ 社をフォーム管理化。追加・削除が管理画面で完結。

| フィールド | 内容 |
|---|---|
| name | 協賛者名 |
| order | 表示順(任意) |

### Instagram について(API 消費なし)
Instagram フィードは microCMS には保存しない。Instagram 側から直接取得するため、上記 4 API とは別枠(microCMS の API 数を消費しない)。

## 4. 要望への対応まとめ

| 要望 | 実現方法 | 日常運用で非エンジニアが自分でできるか |
|---|---|---|
| News 更新 | API② `news` にフォーム入力 | ✅ 完全に自分で |
| アーカイブ(年度別詳細ページ)【新機能】 | API③ `editions-archive` に 1 件登録 → ページ自動生成 | ✅ 新年度の追加は登録するだけ |
| Instagram フィード自動表示 | 取得サービス/Worker 経由で埋め込み(下記6章) | ✅ 初期設定後は自動更新 |
| 年度情報(開催日・募集状況) | API① `site-settings` を編集 → 全ページ反映 | ✅ 完全に自分で |
| 今後のページ増加 | 既存型の中身追加は自分で / **新しい種類のページは開発依頼**(Claude Code 経由) | △ 新種のみ依頼 |

## 5. アーカイブ機能の設計【新機能の詳細】

現行にない「年度別アーカイブ」を新規構築する。

- **一覧ページ** `/archive.html`: 過去大会をカード状に年度降順で並べる(自動生成)
- **個別ページ** `/archive/2024.html` 等: その年の紹介文・代表画像・ギャラリー・受賞作品を表示(1 API レコード = 1 ページ)
- **既存の `2024gallery.html` / `contest2024.html` の内容**を初期データとして API③ に取り込み、順次 `/archive/2024.html` に統合
- ナビゲーション(menubar)に「アーカイブ」項目を追加
- 新年度開催後は、その年の情報を API③ に 1 件足すだけで過去大会入りする運用

## 6. Instagram 連携の方針

Meta の仕様変更により、Instagram の旧 Basic Display API は終了済み。現行の現実的な選択肢は 2 つ:

| 案 | 内容 | 向き / コスト |
|---|---|---|
| **6-a(推奨・簡単)** | フィード埋め込みサービス(Behold / SnapWidget / EmbedSocial 等)の埋め込みコードを設置 | 設定が簡単・無料枠あり。非エンジニアでも初期設定可 |
| 6-b(高度) | Instagram Graph API + Cloudflare Worker でフィードを取得・キャッシュ | 自由度高いが、ビジネスアカウント + Facebook ページ連携 + トークン更新運用が必要 |

**まず 6-a で開始**を推奨。いずれの案でも、Instagram を**ビジネス/クリエイターアカウント**にしておく必要がある点を事前準備として確認する(現状のアカウント種別を要チェック)。

## 8. ブランチ戦略・デプロイフロー(確定仕様)

| ブランチ | 役割 | 反映先 |
|---|---|---|
| `main` | 本番 | https://kadoma-artfes.jp/ |
| `develop` | 開発・検証 | プレビューURL(例: `develop.xxx.pages.dev`) |

- **コード変更**: develop で作業 → プレビュー確認 → main へマージで本番反映(現行フローを踏襲)
- **コンテンツ変更**: microCMS で公開 → Webhook で本番(main)を自動再ビルド → 1〜2分で反映
- コンテンツ編集にメンバーは Git を一切触らない

## 10. リスクと対策

| リスク | 対策 |
|---|---|
| 共有アカウントで個人単位の編集履歴が残らない | 3 アカウント運用ルールで担当を明確化。重要変更は develop で事前確認 |
| 共有パスワードの漏洩・退任 | パスワード管理ツールで共有、退任時は即変更 |
| microCMS 転送量 20GB/月 超過で API 停止 | 画像は Cloudflare 側(リポジトリ/R2)に置き、microCMS には URL のみ格納 |
| 移行中に本番が崩れる | develop + プレビューで完成させてから切替。現行構成はタグ保存で即ロールバック可 |
| URL 変更による SEO 低下 | **URL を完全維持**する設計(`build.format: 'file'`)。変更しないため影響最小 |
| jQuery プラグインと Astro の相性 | Slick 等はクライアントスクリプトとしてそのまま読み込み。M1 で動作確認 |
| Instagram API のアカウント要件・仕様変更 | ビジネスアカウント化を事前確認。まず埋め込みサービス(6-a)で依存を最小化 |
| ビルド失敗でデプロイ停止 | develop で先に検証。失敗しても本番は前回ビルドが残るため無停止 |

## 12. 日常の運用イメージ(移行後)

- **お知らせを出す**: microCMS にログイン → 「お知らせ」で新規作成 → 日付・カテゴリ・本文を入力 → 公開 → 1〜2分でサイト反映
- **今年の開催日を直す**: microCMS →「サイト設定」→ 開催日を書き換え → 公開 → 全ページ一斉反映
- **昨年の展示をアーカイブに残す**: microCMS →「アーカイブ」で新規作成 → 年度・写真・紹介文を入力 → 公開 → `/archive/{年}.html` が自動生成
- **新しい種類のページが欲しい**: Claude Code(GitHub 経由)に依頼 → develop で作成・プレビュー → 確認後に本番反映
